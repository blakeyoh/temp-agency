## Pre-run declaration

- **Enactment state:** RUNNABLE
- **Predicted signature:** each item's specific angle/topic is traceable to arithmetic on a
  string generated before the angle was chosen — not to the model's default top-of-mind
  opener list.
- **Forbidden signature:** ten items that are just the model's stock openers (weather, "what
  do you do," "where are you from") with no string-derivation step behind them.
- **Expected useful failure:** the "random" strings the model generates by hand are not
  actually diverse — the model's own string-writing habit reintroduces bias one level up,
  so several items collide on the same derived angle despite the arithmetic step working
  correctly.

## Exact input

The frozen brief, unmodified, wrapped in the simplified SSoT-DAG system instruction
(paper Appendix D.4, reproduced on the public page):

> You must produce exactly one unique and diverse answer. To do this, first generate a
> complex random string between `<random_string>` and `</random_string>`, and manipulate
> this string to guide any stochastic decisions within `<thinking>` and `</thinking>` tags.
> Then, provide your final answer, enclosed within `<answer>` and `</answer>` tags.
>
> Task: List 10 distinct ways to open a conversation with a stranger at a conference.

**Disclosed adaptation (not in the paper as written):** the paper's DAG prompt is written
for *one* diverse answer per independent generation (used across `k=8` separate samples).
The frozen brief asks for ten items inside a *single* generation. The operator applied the
generate-string→manipulate step **once per item**, inside one continuous pass, rather than
running eight independent full generations. This is an extension of the published
mechanism, not a reproduction of the exact experimental setup, and is named here rather than
silently presented as the paper's own tested condition.

## Observation against contract

- **Predicted signature observed?** Partly. The mapping table shows genuine string→angle
  traceability for each item, and the counterfactual replay confirms the string, not the
  model's preference, moved the outcome for at least one item.
- **Forbidden signature absent?** Yes — no item is a bare stock opener ("what do you do,"
  "where are you from") stated without a derivation step behind it.
- **Useful failure observed?** **Yes, and it matches the pre-run prediction exactly.** Five
  of ten items (1, 2, 3, 9, 10) collided on the same derived angle ("food/drinks station"),
  and only 4 of the 10 available angles were used at all. The arithmetic step worked
  correctly every time; the failure is one level upstream — the operator's own by-hand
  "random" strings were not actually diverse (visibly similar letter-case and digit
  patterns across all ten), so many of them summed into the same bucket. This is the exact
  failure mode the source paper itself measures in frontier models asked to flip a coin
  directly — it did not go away by adding one manipulation step on top of a still-biased
  string generator.
- **Silent fallback detected?** No fabricated derivations found — every row's arithmetic
  checks out against the string as written. But nothing *enforces* that in a future run;
  see Execution trace.
- **First ambiguous operation:** step 1 (string generation) — "complex random string" has no
  operational definition, so its quality (and therefore the whole mechanism's diversity
  ceiling) rests entirely on operator discipline with no check.
- **Faithful enactment:** **FAITHFUL.** The mechanism as defined — generate, then derive by
  arithmetic, never answer directly — was followed exactly, with no post-hoc edits to any
  string after its mapped angle was known. The observed weakness (angle collision) is a
  finding about the mechanism's ceiling, not a failure to enact it.

## Amendment docket

- **Proposal:** *An official E9 run must include at least one counterfactual replay: redraw
  one item's random string under a fresh attempt and confirm the mapped angle and resulting
  text change materially. A replay that leaves the choice unchanged records the run as
  decorative randomness, a contract failure rather than a pass.*
- **Observed source:** this scrimmage's own item-1 replay (`Pl0eSw9c`, mod 10 = 5, "food/drinks" → "role/company") — the check already ran once, inside this record, and passed.
- **Why it serves the existing thesis:** SSoT's whole claim is that the string is
  load-bearing, not decorative. A replay test is the direct, falsifiable check of that claim
  — it adds no second mechanism, only a verification step.
- **Why it does not add a second mechanism:** it changes nothing about how an item is
  produced; it only re-runs step 1 once, after the fact, to confirm the output was sensitive
  to it. Structurally identical to Amendment 4 (E1) and Amendment 3 (A1/C8/M1), both already
  ratified for exactly this reason.
- **Effect on the evidence contract:** adds one required verification step; does not change
  enactment state (remains RUNNABLE).

## Post-scrimmage evidence and amendment — Ruling 23 (2026-09-03)

> Informal, interactive follow-up testing, run live in a Claude Code session after the
> scrimmage above was already on record. Not a formal isolated-operator run like the
> original sixteen — disclosed as such, same as this file's own operator caveat above. This
> section is the evidentiary basis for Ruling 23 / Amendment 9, which changed E9's own
> definition: the seed string must now come from a real generator, never the model.

### Test 1 — eight independent, context-isolated Sonnet subagents

Eight separate subagent calls, zero shared context between them, each asked once for "one
complex random alphanumeric string, about 8 characters." Two of the eight — fully
independent, no memory of each other — returned the **identical string**: `jK9xR2mQ`. Four
of the eight began with the same two characters (`jK`). With 62⁸ (≈218 trillion) possible
8-character strings, an exact duplicate in 8 independent draws is strong direct evidence
that the model's unaided idea of "a random string" occupies a far smaller space than its
size would suggest — worse collision behavior than the original single-session run above,
where every one of the 10 strings was at least superficially distinct.

### Test 2 — one Haiku call for a 250-character string

Asked for one 250-character random string (formatted as 10 lines of 25 characters), Haiku
returned something that read as plausible at a glance. Character-by-character analysis
found **100% of its 214 letters were the alphabet cited in strict consecutive order**
(`abcdefghijklmnopqrstuvwxyz`, wrapping and repeating), with digits and case changes
inserted purely for camouflage. A compression check confirmed it: 0.649 (compressed
size ÷ raw size) versus ~0.876 for a genuinely random string of the same length and
alphabet — meaningfully more compressible, i.e., meaningfully less random. Under length
pressure, the model did not even attempt sustained variation; it fell back to the single
cheapest, most predictable continuation available. This also surfaced a methodological
point: a bucket-coverage check alone (did the derived choice land somewhere different each
time?) does **not** catch this — the shifting alphabet position still produced different
sums and therefore different buckets, so a bucket-only check would have scored this
degenerate string as "diverse."

### Test 3 — two real-random controls

Two 250-character strings were tested as controls: one supplied directly by the
commissioner, and one generated live in-session for full chain-of-custody via:

```python
import secrets, string
"".join(secrets.choice(string.ascii_lowercase + string.digits) for _ in range(250))
```

Both passed every check the model-generated strings failed — no sequential pattern (≈6%
coincidental adjacent-letter match, i.e., chance level, versus Haiku's 100%), full use of
the 36-character alphabet, and compression ratios (0.760, 0.764) close to the real-random
baseline. Both, sliced into ten 25-character chunks and run through this scrimmage's own
sum-mod-10 → category → opener pipeline, improved category spread from the original run's
4-of-10 to **6-of-10**, with no exact chunk-level duplicates in either.

**Residual clumping, disclosed rather than smoothed over:** even this real-random run
produced a 4-of-10 collision (category "compliment") and a 2-of-10 collision (category

(badge/notebook/lanyard/tote bag via a second small calculation on each chunk) also
collided once (two items both landed on "lanyard"). Both collisions are reported as observed,
not resolved by re-drawing or re-deriving — consistent with this file's own standard above

behavior at n=10 (the same birthday-paradox effect, not a sign the real-random source is
flawed), not a new carried defect.

### Ruling

**Ruling 23 / Amendment 9** (full text in `commissioner-rulings.md` and `rules-v2.md` §4):
E9's seed string must come from a real external generator; the model may never invent it.
Checked against the three-test standard in `rules-v2.md` §1 and ruled a legitimate amendment
to E9's own thesis, not an absorption into E1 — E1 looks up a choice directly from a stamped
seed index with no manipulation step; E9 still requires the model to legibly derive its
answer from a given string, which is what makes it a different mechanism even once both sit
on real entropy. Commissioner's own words, on the record: *"I don't think E9 would win in
this tournament without the external randomness, but again, this is somewhat different than
E1. My call is to keep E9 but require the use of a generator. It is different than both, but
it's better than the original E9 idea."*

**What remains open:** the manipulation step — deriving the answer from the given string —
is still entirely unenforced. Nothing checks that a model's stated arithmetic trace is the
real cause of its answer rather than a justification invented after the fact. This amendment
fixes the string's origin only.
